SVN Terminal Commands - Safety Guide

Commands sorted by how much damage they can do, written for artists, UX and UI people who work in SVN day to day. When this guide says to ask a developer, that is the safe choice, not a failure.

Quick reference

The commands you will use most. Each one is explained in its tier below.

CommandUse it toTier

svn log -l 10See the last 10 commitsTier 1

Ask a developer first

These can affect other people's work or the whole project, and some can't be undone by you. If you aren't sure, stop and ask. Nothing in this guide is urgent enough to risk shared work.

Command or situationWhy to ask first
svn merge (any form)It changes many files at once and can create conflicts that take hours to untangle. This includes bringing changes from the main line into your R&D branch, and bringing your R&D work back.
svn switchIt repoints your whole project folder to another branch. With local edits it can conflict. For R&D, use a separate checkout instead (see R&D branch).
svn update -r NIt moves your folder to an old revision. Editing or committing from there causes confusion.
svn update --accept theirs-fullIt silently throws away your edits in every conflicted file.
svn upgradeOne-way change. Older SVN tools may no longer open the folder afterwards.
svn delete, move, mkdir or copy on a server addressThese act on the shared server immediately and everyone sees them. The only exception is creating your own R&D branch, as described in R&D branch.
svn propset, ignore rules, svn:externalsProject-wide settings. A wrong value affects everyone's checkout.
svn unlock --forceBreaks a lock held by someone else, who could lose work.
Reversing a commit, yours or someone else'sThe reversal becomes a new commit that everyone receives. A developer checks nobody depends on it first.
You committed to the wrong branchFixing it needs reverse commits and merges. Stop and tell a developer. See Fixing mistakes.
A conflict in a scene, prefab, texture, model or any binary file, or a tree conflictThese can't be merged safely by hand, and it's easy to lose someone's work. See Fixing conflicts.
Changing Unity project settings, packages or the ProjectSettings folderThese settings apply to everyone who opens the project.
svn status shows far more changes than you madeDon't commit. It is often generated folders such as Library or Temp, or a wrong folder. A developer can check and set up ignore rules.
"Authorization failed" or "forbidden"Your account may be missing access to that location. Don't look for another login.
Anything not in this guideLook it up with svn help <command> if you like, but ask before running it.

Daily workflow

A safe order for a normal working session.

  1. Run svn status to see the state of your folder before you start.
  2. Run svn update to get the latest changes. If any file shows C, stop and read Fixing conflicts.
  3. Do your work. Rename or move tracked files with svn move, not in Finder.
  4. Run svn status again. A ? is a new file you may need to svn add. A ! is a file that has gone missing.
  5. Run svn diff and read what you are about to publish.
  6. Run svn commit -m "Short, clear message".
  7. If the commit fails with "out of date", someone committed first. Run svn update, deal with any conflicts, then commit again.

Tier 1: Read-only (always safe)

These don't change your files or the repository.

CommandWhat it does
svn statusCompares your files to the last update and lists what you changed. First-column letters: M modified, A added, D deleted, ? not under version control, ! missing, C conflict. Reads local data only.
svn status -uSame list, plus a column marking files changed on the server since your last update. Contacts the server, so it needs your login.
svn infoShows which repository URL, branch and revision your folder is on, and who last changed it. Answers "which branch am I on?"
svn logShows commit history: revision, author, date and message. -l N limits to N entries, -v lists changed files, -r A:B selects a revision range, --stop-on-copy stops where the branch was created, -q gives a short list.
svn diffPrints your uncommitted changes line by line. Add a file name to see one file. -r A:B compares two revisions, -c N shows what revision N changed.
svn blame fileShows each line of a text file with the revision and author who last changed it. Useful for finding who to ask about a change.
svn cat -r N filePrints a file as it was at revision N, without touching your copy.
svn ls <url or path>Lists files and folders at a location, even on the server, without checking anything out. -v adds revision and author.
svn list -RSame as ls, recursive. Can be very long on a big project, so pipe it into head or less.
svn proplist -v / propgetShows properties attached to files or folders, such as svn:ignore, svn:externals and svn:needs-lock. Viewing is safe. Changing them is for developers.
svn help <command>Prints full options for any command.

Tier 2: Local changes, easy to undo

Nothing reaches the server. You can reverse these before committing.

CommandWhat it does
svn add fileStarts tracking a new file. Nothing goes to the server until you commit. Undo with svn revert file.
svn delete fileMarks a tracked file for deletion and removes it locally. The server learns about it at commit. Undo with svn revert file before committing.
svn move old newRenames or moves a file and keeps its history. Prefer it over moving the file in Finder, which makes SVN see one file deleted and another added.
svn updateDownloads other people's changes and merges them into your files. If you edited the same lines as someone else you get a conflict (C). Run svn status first.
svn export <url> folderDownloads a clean copy of a branch or folder with no .svn metadata. Writes to a new folder only, so it's harmless.
svn cleanupRepairs your folder after a crash or interrupted update and removes stale locks. Fixes "working copy locked" errors.
svn resolve --accept working fileTells SVN you've fixed a conflict so it stops flagging it. It doesn't choose the right content for you. Use it only on simple text files you've checked. For scenes, prefabs and binary files, ask a developer first.

Tier 3: Risky, can lose your local work

Check svn status before running either of these.

CommandWhat it does and why it's risky
svn revert fileThrows away your uncommitted edits and restores the last committed version. Permanent. Nothing is saved anywhere, so you can't get your edits back.
svn revert -R .The same for every changed file in the current folder and below. Read the svn status list first.

Tier 4: Changes the shared server

Visible to everyone on the team.

CommandWhat it does and why it's risky
svn commit -m "message"Sends your changes to the server as a new revision everyone sees. It can't be erased, only undone with a new reverse commit. Run svn status and svn diff first, check the branch with svn info, and write a clear message.
svn lock filePrevents others from committing that file until you unlock it. Common for Unity scenes, prefabs and binary assets. A normal commit releases the lock for you.
svn unlock fileReleases a lock you hold. Never use --force on someone else's lock.
svn copy <url> <url> -m "msg"Creates a branch on the server. For you, this is only for making your own R&D branch in the location a developer gave you. Follow R&D branch. A typo leaves a stray folder on the shared server.

Habits that prevent most mistakes

  1. Run svn status before any command in Tier 3 or 4.
  2. Run svn diff before commit and read what you're about to publish.
  3. Run svn info before committing if you use more than one folder or branch, and check the URL line.
  4. Before svn revert -R ., read the svn status list, because it's the only warning you get.
  5. Before anything risky, save your edits with svn diff > my-changes.patch.
  6. If something looks wrong, or it isn't in this guide, stop and ask. Nothing in Tier 1 or 2 can hurt.

R&D branch: your own sandbox

A branch is your own copy of the project on the server. You can experiment and commit as often as you like without touching what the team uses. It's safe as long as you create it in the right place and keep it separate from your normal work. Bringing results back into the main line is a developer job.

Before you start

  • Ask a developer or lead which branch to copy from, where personal R&D branches live, what to name yours, and whether your account is allowed to create one. Rules differ between teams, and a wrong branch clutters the shared server.
  • Large projects take a while to check out the first time. Plan for that.

Steps

  1. Get the address of what you are copying. In your normal project folder run svn info --show-item url (SVN 1.9 or newer, otherwise run svn info and read the URL line). Check with the developer that it's the right source.
  2. Create the branch on the server: svn copy "<source-url>" "<your-branch-url>" -m "Create R&D branch: <short purpose>"
    This is instant and downloads nothing. Read both addresses twice before pressing Enter, because everyone sees the new branch immediately. If SVN says the destination's parent folder doesn't exist, stop and ask a developer instead of adding options.
  3. Confirm it exists: svn ls "<your-branch-url>" should list the project's files.
  4. Check it out into a new, clearly named folder: svn checkout "<your-branch-url>" project-rnd-yourname
    Don't use svn switch on your normal project folder. A separate checkout keeps your main work and your R&D apart.
  5. Work in the R&D folder using the daily workflow. Before every commit run svn info and check that the URL line ends with your branch name. A commit goes wherever the folder it's run in points.
  6. When the R&D is finished, or you want to share it, tell a developer. They can review it and merge your branch, or just selected files, into the main line. Ask them to delete the branch when it's no longer needed.

Rules for R&D folders

  • Give the two folders obvious names, for example project-main and project-rnd-yourname.
  • Don't run svn merge or svn switch in either folder. Both are developer jobs.
  • Don't copy files by hand between the two folders to move work across. It can silently overwrite someone's newer work in the main folder. To bring R&D work into main, ask a developer.
  • Your branch slowly falls behind the main line. Updating it with newer main-line changes is a merge, so ask a developer. Short experiments rarely need it.
  • Commit to your branch as often as you like, but only what you need. Don't commit generated folders (see Unity basics).

Fixing mistakes

Anything that has been committed stays in the repository history, so it can be recovered by a developer. The only work that can be truly lost is uncommitted edits, which is why Tier 3 commands need care.

SituationWhat to do
I want to throw away my uncommitted edits to a filesvn revert file

This is permanent. If there's any doubt, save a copy first with svn diff file > backup.patch.

I want to save my edits before something riskysvn diff > my-changes.patch

This writes every uncommitted change to a text file. Re-apply it later with svn patch my-changes.patch. New files that aren't added yet are not included, and binary files like textures are not saved properly, so copy those somewhere by hand.

I deleted a file in Finder and it shows !svn revert file

This brings back the last committed version. For a folder use svn revert -R folder.

I forgot to add a file (or its .meta) before committingsvn add file, then svn commit -m "Add missing file"
Commit says a file or folder is "out of date"Someone committed before you. Run svn update, deal with any conflicts, then commit again.
SVN says the working copy is lockedsvn cleanup

This usually happens after an interrupted update or a crash.

I locked a file and forgot to unlock itsvn unlock file

If someone else holds a lock you need released, ask them or a developer.

I committed something wrong, deleted a file and committed it, or committed to the wrong branchStop and ask a developer. Don't commit anything else. Tell them three things: the revision number (find it with svn log -l 5), the branch address (the URL line from svn info), and what you meant to do. Whatever you committed stays in history, so it can be reversed.
An update left conflicts and I'm unsureDon't commit. Follow Fixing conflicts.

Fixing conflicts

A conflict happens when you and someone else changed the same file in overlapping ways. SVN won't guess, so it marks the file C and asks you to decide. Nothing is lost: both versions are kept next to your file.

What to do

  1. Find conflicted files with svn status. They show C in the first column and also appear in the output of svn update.
  2. Don't commit. Don't delete the extra files SVN created next to the conflicted file (listed below).
  3. Check what kind of file it is. If it's a scene, prefab, material, texture, model, PSD, data or config file, or any other binary or Unity asset, don't try to fix it by hand. Go to "Before you ask for help" below.
  4. Only if it's a plain text file such as notes or documentation, and the change is small and you understand both sides, open it and search for <<<<<<<. Keep the lines that are correct and delete the marker lines. Save the file, then run svn resolve --accept working file.
  5. Run svn diff file to check the result, then commit.
Extra fileWhat it holds
file.mineYour version of the file, as it was before the update.
file.rOLD (for example file.r100)The server version your edits were based on.
file.rNEW (for example file.r105)The latest server version.

Before you ask for help

  • Copy the output of svn status and note the path of each conflicted file.
  • Copy file.mine to a safe place outside the project folder so your version can't be lost.
  • Note which branch you're on (the URL line from svn info).
  • Find out who made the other change with svn log -l 5 file. Agree together which version to keep. Only after that, a developer or you can keep one side with svn resolve --accept mine-full file or --accept theirs-full file. The second one discards your edits to that file.

Tree conflicts

A tree conflict happens when someone moved, renamed or deleted a file you edited. svn status shows an extra line starting with > under the file. Don't use any --accept shortcut. Ask a developer.

Common errors

Messages you may see, what they mean, and who should fix them. Message wording can vary slightly between SVN versions.

MessageWhat it means and what to do
Working copy locked or E155004, "already locked"You can fix A previous command was interrupted. Run svn cleanup, then try again.
... is out of dateYou can fix Someone committed before you. Run svn update, deal with any conflicts, then commit again.
... is not a working copyYou can fix You're not inside a project folder. Use cd to go into it and check with svn info.
... is not under version controlYou can fix The file is new. Add it with svn add file. If the folder is also new, add the folder, which adds what's inside.
path not found or non-existent in revisionYou can fix A typo in the address, or the path doesn't exist there. Check the parent with svn ls.
Unable to connect to a repository or Could not resolve hostnameYou can fix A network problem. Check your VPN and Wi-Fi and try again. If it keeps failing, ask IT.
... is locked by user ...Contact the person Someone else holds a lock on that file. Message the person named in the error. Don't force the lock.
Commit blocked by pre-commit hookRead, then ask A server rule rejected your commit, for example because of the message format or a forbidden file. Read the message. If it's unclear, ask a developer.
Authorization failed or Access forbiddenAsk a developer Your login may be wrong or your account may lack access to that location. Try again once, carefully, then ask. Don't look for another login.
Tree conflictAsk a developer See Fixing conflicts.
svn: command not found or command not found: svnAsk IT or a developer The SVN command-line tools aren't installed or aren't on your path.

Unity basics

Habits that keep a Unity project healthy under SVN.

TipWhy it matters
Commit each .meta file together with its asset. A new folder has its own .meta, so add both.Unity stores an asset's GUID in its .meta file. If the file is missing or changes, references to that asset break for everyone.
Move and rename with svn move, on both the asset and its .meta, ideally with Unity closed. If unsure, ask.Moving in Finder makes SVN see one file deleted and one added, and the .meta may not follow.
Never commit generated folders: Library, Temp, Obj, Logs and usually UserSettings. If they show up as ? in svn status, don't add them, and ask a developer to set up ignore rules.They are rebuilt automatically, are huge, and cause constant conflicts.
Avoid svn add --force . at the project root.It adds every unversioned file below it, including generated folders that aren't ignored. Add specific files or folders instead.
Lock scenes, prefabs and large binaries before editing them if others might touch them: svn lock fileThese files merge badly. A lock stops others from committing the file. A normal commit releases the lock for you.
Close Unity during svn update and when moving or renaming files.Unity can regenerate .meta files or reimport assets while SVN is writing files, which causes odd conflicts or missing .meta files.
After Unity finishes importing, run svn status and read the list before committing.Unity can rewrite .meta files during import. Commit only the changes you meant to make.
Don't change project-wide settings: Project Settings, packages, or anything in the ProjectSettings folder. Ask a developer.These settings apply to everyone who opens the project.

Handy variations

Useful forms of the commands above, including a few that combine commands with grep or less.

CommandWhat it does
svn status -qLists only tracked files with changes and hides the ? files.
svn status | grep '^?'Lists only new files that SVN doesn't track yet.
svn status | grep '^!'Lists only missing files.
svn status | grep '^C'Lists only conflicted files.
svn log -l 10 -vShows the last 10 commits with the files each one changed.
svn log --search "word" -l 20Finds commits whose message or author contains a word, and limits the output to 20 entries. Needs SVN 1.8 or newer.
svn log --stop-on-copy -qLists the revisions on this branch only. The last one is where the branch was created.
svn diff | lessShows a long diff one page at a time. Press q to quit.
svn diff --summarize -r A:B .Lists only the names of files that differ between two revisions, without the line changes.
svn info --show-item urlPrints only the branch URL. Use revision instead of url for the revision number. Needs SVN 1.9 or newer.
svn diff > my-changes.patchSaves your uncommitted text edits to a patch file as a backup. Restore with svn patch my-changes.patch.

Glossary

Plain meanings for the terms used in this guide.

TermMeaning
RepositoryThe shared server copy of the project, with its full history.
Working copyThe folder on your computer that you edit. It is linked to the repository through a hidden .svn folder.
RevisionA numbered snapshot of the whole repository. Every commit creates the next number, for example r105.
HEADThe latest revision on the server.
BASEThe revision your folder was last updated to. svn diff compares your files against it.
CheckoutCreating a working copy by downloading a project from the repository for the first time.
CommitSending your local changes to the repository as a new revision.
UpdateDownloading other people's changes into your working copy.
TrunkThe main line of development. Most teams keep their stable or latest code here.
BranchA copy of the code on the server where work can happen separately from the main line.
R&D branchA branch you create for your own experiments, checked out into its own folder. See R&D branch.
TagA named copy of the code at one moment, usually a release. It isn't meant to be changed.
MergeApplying the changes from one branch to another. A developer job in this guide.
ConflictTwo people changed the same file in overlapping ways, and SVN needs a person to choose what to keep.
LockA claim on a file that stops others from committing it until you release it.
PropertyA named setting attached to a file or folder, such as svn:ignore.
